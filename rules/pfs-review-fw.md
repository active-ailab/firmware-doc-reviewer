# 固件侧 PFS Review 规则

本规则用于判断固定 PFS 是否正确承接可访问、唯一的基准 PRD，且是否具备固件开发拆分、估时和验收条件。输出双向追溯、差异、Block、关闭动作和开发准备度结论。

## 1. 输入与证据

评审对象为 PFS，支持飞书 Sheet、飞书 Docx 和 Markdown。基准证据为 PFS 明确引用的 PRD 及其与当前需求直接相关的明确关联资料。

开始评审前，PFS 必须包含可解析、可读取且能唯一定位本次基准 PRD 的引用。可接受 PRD 直链、飞书富文本 PRD 提及或其他已支持且可唯一解析到 PRD 的引用。

以下情况直接停止评审并说明原因：

1. 未找到基准 PRD 引用；
2. PRD 无法读取；
3. 存在多个候选 PRD 但无法确定基准；
4. PFS 与 PRD 的项目或功能范围明显不一致。

交互稿、协议、版本说明、验收材料、机型资料和其他非关键参考资料无法访问时，记录为证据缺口；仅在实质阻断当前 PFS 的规格承接、开发拆分或验收时设为 Block。

默认只读：不修改 PFS 或 PRD，不创建 Jira，不提交代码，不发布固件。默认不核查代码；仅在用户明确要求，或 PFS 声称复用既有能力、无影响且该事实存在实质争议时，在附录中进行实现可行性确认。

## 2. Sheet 还原与活跃需求行

飞书 Sheet 必须先按以下顺序处理，再进行任何字段完整性、追溯或评分判断：

1. 读取原始单元格、表头、合并区域、富文本引用和下拉枚举；
2. 将合并单元格左上角的值作为同一逻辑分组的继承上下文；
3. 排除表头、说明行、空模板行，以及仅有下拉校验而没有实际规格内容的预留行；
4. 以实际规格内容识别活跃需求行，通常以 `Description` 为主要证据；
5. 在还原后的分组、模块与项目上下文中建立 PFS 与 PRD 的追溯。

不得将合并单元格产生的表面空值直接判为缺失。`Feature`、`Category`、`Project` 等分组字段可由首行向后续活跃需求行继承。若合并还原后仍无法确定实际需求条目的规格、来源或范围，才记录为问题。

## 3. 固定字段的评审定位

历史固定 PFS 结构可包括：

```text
Category
PRD Index / PRD Description
Feature / Feature Owner
Index / Description
执行程度 / PFS Comments
CDVT / DEV / DVT / SI&T / IT
Project
```

字段按以下口径使用，不因辅助字段为空机械扣分或设 Block：

| 字段 | 评审定位 |
|---|---|
| `Description` | PFS 规格的主证据；核验功能、条件、参数、边界、异常和验收行为。 |
| `执行程度` | 用户填写的 `SHALL/SHOULD/MAY` 承接声明；必须依据 PRD 核验其合理性。 |
| `PRD Index` | 有值时优先作为追溯锚点；无值时不直接判追溯失败。 |
| `PRD Description` | PRD 语义的辅助证据。 |
| `Feature` | Description 所属的大致功能模块，用于缩小 PRD 查找范围；可按合并分组继承，非必填。 |
| `Index` | 仅用于 PFS 内部条目定位、报告编号和人工沟通；不得假定可对应 PRD 编号。 |
| `PFS Comments` | 例外、取舍、待确认或关闭动作的条件性补充信息。 |
| `Feature Owner` | 跨端协作、遗留关闭或责任分派需要时的条件性责任信息。 |
| `Category`、`Project` | 分组与项目范围的辅助上下文。 |
| `CDVT`、`DEV`、`DVT`、`SI&T`、`IT` | 阶段参考信息；除非业务语义已明确，空值不扣分。 |

## 4. 评审顺序

1. 阅读 PFS、基准 PRD 与理解当前需求所必需的明确关联资料。
2. 对 Sheet 完成合并单元格和分组继承还原，识别活跃需求行；对 Docx 或 Markdown 识别对应的段落、表格、引用和源位置。
3. 从 PRD 拆分出可独立追溯的最小需求项，提取适用范围、功能、条件、参数、边界、异常和验收行为。
4. 以 `Description` 为主规格证据，结合 `PRD Index`、PRD 引用、章节、原文和 `Feature` 模块上下文建立 PRD 与 PFS 的双向追溯。
5. 核验 PFS 的执行程度声明是否与 PRD 的强制性、条件性或可选性一致。
6. 识别差异、Block、待确认项及其实际影响，判断是否支持开发拆分、估时和验收。
7. 仅对适用维度评分，并以固定模板输出结论和关闭动作。

支持 PRD 与 PFS 的 1:1、1:N 和 N:1 映射。出现拆分或合并时，必须核验 PRD 的语义、约束和验收条件是否被保留。

## 5. 执行程度核验

`执行程度` 是 PFS 填写者对需求强度的声明，不是准入条件，也不是自行评分的依据。评审必须以 PRD 为真值核验：

| PRD 语义 | PFS 填写 | 判定 |
|---|---|---|
| 明确本期强制实现 | `SHALL` | 一致。 |
| 明确本期强制实现 | `SHOULD` / `MAY` | 可能降级；根据是否造成漏做、不可验收或范围偏差判定差异和影响。 |
| 明确条件性或可选 | `SHALL` | 可能过度承接；转产品确认其范围和版本。 |
| PRD 未明确强度 | 任意值或空 | 不机械判错，仅记录依据不足或待确认。 |

`执行程度` 为空，或与 PRD 表面不一致，均不得单独扣分或设 Block。只有其实际导致核心需求漏承接、无授权范围新增、无法开发拆分或无法验收时，才按第 6 节分类为差异或 Block。

`PFS Comments` 和 `Feature Owner` 仅在存在例外、未决事项、跨团队依赖、待关闭动作或责任分派时要求。它们为空时，只有因此无法关闭实际风险或无法明确必要责任，才记录问题。

### 5.1 性能指标归属

仅当 PRD 明确表明性能指标与固件的输入、输出、调用、版本或设备侧行为存在关系时，才在固件侧 PFS 中记录并判断其归属。与固件无明确关联的算法或其他端指标不记录、不展示、不评分也不验收。对有关联的指标，按计算或产生位置、直接责任端、输入输出关系和日志证据标为固件主责、其他端依赖或待确认；不得仅根据指标名称推定归属。

- 固件主责指标（如设备端时延、功耗、内存、帧率或设备端处理能力）进入固件规格、评分和 Block 判断。
- 算法或其他端主责指标若与固件无明确关联，完全不进入固件侧 PFS 报告；有关联时不计入固件实现评分，也不验收其指标或实现，仅核验对应固件依赖是否明确。
- 有关联的其他端指标仅记录固件所需的输入、输出、调用或版本条件，不评估或验收其他端指标、实现或交付；只有该固件依赖未定义且实际阻断固件开发、日志观测或固件验收时，才影响固件结论。
- 已明确与固件有关但归属无法确定时才列为待确认；只有该不确定性实际阻断固件开发、依赖对齐或固件验收时才设 Block。

## 6. 双向追溯、差异与 Block

### 6.1 双向追溯

PRD → PFS：检查适用于当前项目的 PRD 最小需求项，是否被 PFS `Description` 完整承接。`PRD Index` 有值时优先定位；无值时，根据 PRD 引用、章节、原文与 Description 的可证实语义建立对应，`Feature` 仅用于缩小模块范围。

PFS → PRD：检查每条实际 PFS 规格是否有 PRD 来源或需求依据。`Index` 只用于定位 PFS 条目，不得作为 PRD 映射键。

### 6.2 差异定义

| 类型 | 定义 | 处理 |
|---|---|---|
| D1 漏项 | PRD 明确要求，PFS 未承接。 | 记录缺失的 PRD 证据、影响和关闭条件。 |
| D2-A 授权细化 | PFS 在 PRD 已授权范围内的实现细化。 | 不扣分、不设 Block。 |
| D2-B 未授权新增 | PFS 存在无 PRD 来源且超出授权范围的内容。 | 转产品确认范围、版本与验收归属。 |
| D3 冲突 | PRD 与 PFS 对同一事项的功能、条件、参数、边界或行为不能同时成立。 | 记录双方证据并明确需确认的真值。 |
| D4 模糊 | 已有内容但无法归属、无法编码或无法验收。 | 补充可追溯规格、条件或验收证据。 |

### 6.3 Block

以下情况为 Block：

- 基准 PRD 缺失、不可读或不能唯一确定；
- PRD 核心强制需求未被 PFS `Description` 承接；
- 关键参数、行为或边界存在 D3 冲突；
- PFS 无法支撑关键功能的开发拆分或验收；
- 关键 PFS 条目的来源完全无法解释。

以下情况不得单独自动设为 Block：

- 合并单元格造成的表面空值；
- `Feature`、`Feature Owner`、`PFS Comments`、阶段字段或其他辅助字段为空；
- `Index` 不能对应 PRD；
- `执行程度` 为空或仅表面不一致；
- 非关键参考资料不可访问。

## 7. 评分与结论

评分仅为辅助质量指标，不能以高分掩盖 Block、核心 D1 或关键 D3。仅对适用维度评分，按适用权重折算为 100 分：

| 维度 | 满分 | 评审问题 |
|---|---:|---|
| 基准与范围一致性 | 20 | 基准 PRD 是否唯一可读，项目与功能范围是否一致？ |
| PRD 双向追溯 | 25 | PRD 需求是否承接，PFS 规格是否有来源，拆分/合并是否保留语义？ |
| 规格完整性与一致性 | 25 | Description 是否覆盖可编码的功能、条件、参数、边界、异常和行为？ |
| 范围承接与可开发性 | 10 | PFS 对 PRD 的范围承接是否支撑开发拆分与验收？执行程度仅作为待核验证据，不单独计分。 |
| 开发拆分与责任闭环 | 10 | 是否可拆分、估时，例外或跨端依赖是否可关闭？ |
| 验收准备度 | 10 | 是否能形成可执行验收项及相应证据？ |

判定规则：

- 通过：总分不低于 80、Block 为 0，且无未确认的核心 D1/D3；
- 有条件通过：总分 70–79、Block 为 0，可开始技术准备，但须完成报告中的必补项；
- 不通过：任一 Block，或总分低于 70。

分数表示规格承接与开发准备度，不表示项目优先级、产品价值或研发工期。
