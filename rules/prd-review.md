# PRD Review 规则

本规则用于判断 PRD 是否具备进入固件研发阶段的条件。输出研发可执行的结论、Block、风险和补齐动作。

## 1. 输入与证据

最小输入：

1. PRD 链接或正文；
2. 目标产品或平台，以及涉及的 App/固件范围；未列目标机型或项目清单时，默认覆盖所有支持该功能的项目机器；固件版本和 App 版本仅在 PRD 明确涉及版本差异、升级、降级、兼容或灰度时要求；
3. 涉及的端：手表固件、App、云端、算法、第三方 SDK 中的至少一项。

可选证据包括交互稿、状态矩阵、协议定义、翻译清单、语音资源说明、埋点定义、机型或硬件能力资料、OTA 或回滚策略、历史数据样本、验证入口，以及第三方 SDK 版本和降级约束。

### 1.1 先阅读关联文件

评估当前 PRD 前，先处理它明确关联的资料：

- 关联其他 PRD 时，先阅读并理解前置 PRD，再判断当前 PRD 的目标、继承关系、变更边界和新增内容。
- 关联协议、交互稿、流程说明、版本说明、验收文档或其他非 PRD 文件时，先阅读与当前需求相关的内容。
- 关联文件继续引用其他必要文件时，继续阅读，直到具备理解当前 PRD 所需的上下文。
- 报告中记录实际阅读的关联文件及其作用。
- 无法访问或无法理解的前置文件标记为“待确认”；只有其缺失影响需求边界、实现、兼容、安全或验收时才设为 Block。

### 1.2 代码仓库不是默认输入

默认只依据 PRD 及其明确引用的产品、设计、协议、版本和验收资料，不检索代码仓库，也不以当前代码是否存在某模块决定 PRD 是否通过。

仅在以下情况启用独立的“实现可行性确认”附录：

- 用户明确要求核对代码；
- PRD 声称复用既有能力或无影响，但该事实存在实质争议；
- 评审结论必须确认某项已有能力是否存在。

附录必须记录仓库、分支或版本、路径和证据时间。仓库发现不能覆盖已确认的产品需求边界；冲突项回到 PRD 由责任人确认。

## 2. 评审顺序

按以下顺序执行：

1. 完成当前 PRD 和必要关联文件的阅读。
2. 将需求拆成可独立归属和验收的最小项，识别每项的直接责任端、固件与其他端之间的依赖方向及证据状态。
3. 按责任端分别判断设备形态和变更形态；无法识别的内容列为“待确认”，不擅自补全。
4. 提取“用户动作 → App/云/算法输入 → 固件状态与数据 → UI/日志输出 → 失败与恢复”的端到端链路。
5. 在需求涉及跨端版本、兼容或升级时，建立对应的版本组合矩阵。
6. 只评估适用的固件维度，以及会影响固件交付的跨端依赖；记录不适用或无影响的依据。
7. 按评分表给分，单独列出 Block、证据、影响和关闭条件。
8. 按固定输出顺序生成报告，所有推断均标注为推断。

### 2.1 端侧归属与依赖

端侧识别是内部评审步骤，结论融入现有评分、依赖、验收和待确认项，不额外改变报告结构。

对每个最小需求项按以下证据顺序确定直接责任端：明确的职责拆分或范围声明、页面或能力归属、数据或控制的提供方与消费方、验收对象和上下文。不得仅凭章节标题、端到端链路中的出现位置或单个端名判定归属。

将与固件有关的内容分为：

- 固件主责项：由固件直接实现、承载或交付，进入固件主评估。
- 固件依赖其他端：固件消费其他端提供的数据、命令、配置、资源、能力、版本或状态，作为次级评估项。
- 其他端依赖固件：其他端消费固件提供的数据、状态、能力、版本或产物，作为次级评估项。
- 纯其他端事项：不进入固件评分，也不进入报告正文；仅在其影响固件边界、依赖、兼容或验收闭环时，转化为必要的跨端依赖提醒。

次级评估项不设置独立分数，按实际影响归入端间协议、版本兼容、可靠性、依赖治理或验证闭环。只有缺口实质影响固件实现、兼容、安全或验收时才扣分或设为 Block。

同一业务目标可以由不同端承担不同变更形态。端侧证据冲突或责任不明确时，记录不同解释、影响维度和关闭责任人；在确认前不得把其他端新增能力推定为固件新增能力。

## 3. 设备形态与默认交互

- PRD 未特别说明时，默认按有屏设备评审设备端页面、交互状态、布局、文本或多语言展示和 UI 验收。
- PRD 未列目标机型或项目清单时，默认按所有支持该功能的项目机器评审；未明确写出支持条件时，默认设备具备支持条件。不因缺少机型清单或支持条件扣分或设 Block。
- PRD 明确为无屏设备时，跳过设备端 UI 维度，不因缺少页面、交互稿、布局或本地展示词条扣分或设 Block；仍评审设备能力、协议、可靠性、日志和验证；版本相关内容仅在 PRD 明确涉及时评审。
- 同一需求覆盖有屏与无屏设备时，分别给出适用项和结论。
- PRD 未提出设备专属或特殊交互时，默认复用既有系统交互逻辑，不要求设备能力清单，也不因未描述按键、表冠、触控等固定系统逻辑扣分。
- PRD 明确提出特殊按键、表冠、触控、语音、震动、提示音或其他设备差异时，再评审其适用范围、行为和验收。

## 4. 变更形态

按最小需求项及其直接责任端分类，再启用评审维度。不得给整个 PRD 粗略套用单一变更形态，也不得把其他端的变更形态用于触发固件检查项。

| 变更形态 | 示例 | 评审重点 |
|-|-|-|
| 既有展示资源替换 | 在已有页面替换固定词条、名称或颜色，不改变数据、流程或页面组织 | 核对复用边界；确认不新增页面、翻译范围、语音资源、协议、持久化或运行时逻辑后，不适用维度不扣分、不设 Block。 |
| 既有能力的配置或流程调整 | 调整已有设置、提醒阈值或显示规则 | 状态机、数据契约、版本兼容和可验证性；页面、翻译或语音输入未变化时不机械启用相关评审。 |
| 新增页面、翻译或语音资源 | 新页面、新页面结构、多语言词条或语音播报 | 页面数量与复杂度、翻译范围、语音资源和设计稿输入，以及版本兼容、状态机和验证。 |
| 新增数据、算法、通信或持久化能力 | 新传感器数据、协议字段、同步任务、算法或本地数据库 | 全量启用评分维度；可靠性和回滚缺失可成为 Block。 |

结合章节位置和上下文判断语义，不按关键词机械触发高风险分支。“影响范围”“现有路径”“同步修改或适配”中的导航或调用链路，默认表示既有链路或待核对位置。只有明确出现新增、创建、首次提供、无现有承载，或明确新增交互或资源时，才归为新增能力。上下文冲突时，写出不同解释及其评分影响。

“不适用”必须有可追溯依据。与固件无关的维度直接跳过，不输出、不评分、不形成待确认项或 Block；只有适用维度参与评分，最终按适用维度权重折算为 100 分。适用但证据不足时标记为“待确认”，仅当未知项影响实现、安全、兼容或发布决策时才扣分或设 Block。

## 5. 评分与 Block

评分对象以固件主责项为主，并纳入会影响固件交付的次级依赖项。纯其他端事项不进入固件评分，也不输出到报告正文；其他端自身的信息缺口也不直接形成固件 Block，除非该缺口会阻断固件实现、兼容、安全或目标环境验收。

总分 100 分：

| 维度 | 满分 | 评审问题 | Block 阈值 |
|-|-|-|-|
| 设备能力与需求边界 | 15 | 目标设备、需求边界、所需传感器或外设、权限、前后台、离线能力和不支持范围是否明确？ | 0–5 |
| 端间协议与数据契约 | 15 | 需求是否涉及固件与 App、云、算法或 SDK 之间的数据、命令或状态协作，并需要后续各端对齐？不要求 PRD 在本阶段完成技术契约设计。 | 不单独设 Block |
| 版本、兼容与升级策略 | 15 | 仅在 PRD 明确涉及版本差异、升级、降级、兼容或灰度时，评估最低 App/固件版本、适用范围、混合版本、OTA、回滚和历史数据行为；未涉及则跳过，不纳入评分。 | 0–5 |
| 功能流程与状态机 | 15 | 触发、运行、暂停或中断、恢复、超时、重复操作和后台切换是否可实现且可观测？ | 0–5 |
| 页面、翻译与语音资源输入 | 15 | 是否涉及新增页面、页面复杂度变化、翻译、多语言、语音资源或设计稿输入？ | 不单独设 Block |
| 安全、可靠性与异常恢复 | 10 | 数据校验、隐私、异常输入、断连、重启、升级失败、持久化一致性和恢复路径是否明确？ | 0–3 |
| 可验证性与发布闭环 | 10 | 真机、模拟器或单测入口、日志、验收用例、灰度和回滚判据是否明确？ | 0–3 |
| 实现范围与依赖治理 | 5 | 影响模块、责任端、外部依赖、前置条件和本期或后续范围是否收敛？ | 0–2 |

判定规则：

- 通过：总分不低于 80、Block 为 0，且无未确认的安全或兼容风险。
- 有条件通过：总分 70–79、Block 为 0；可启动技术方案，但须完成报告中的必补项。
- 不通过：任一维度落入 Block 区间，或总分低于 70。

强制 Block：PRD 明确涉及特定设备、版本、升级、降级、兼容或灰度策略，但对应范围或恢复条件缺失；升级后不可恢复或数据损坏风险未定义；固件及其必要跨端依赖无法在目标环境验收。端间协议与数据契约、页面翻译语音资源和设计稿输入的缺口默认作为提醒或待确认项，不单独形成 Block。未明确涉及上述条件时，不因缺少目标机型清单、固件版本或 App 版本设 Block。

分数只表示信息完整度和风险可控度，不表示项目优先级或研发工期。

## 6. 输出契约

报告按以下顺序输出；与固件无关的维度、事项和专属明细直接跳过，不输出“不适用”。

## 7. 关键检查清单

只在变更形态适用时使用对应检查项。

### 7.1 设备能力与状态

- 是否提出超出既有系统逻辑的设备能力或特殊交互？
- 相关传感器或外设不可用、低电量、运动中、锁屏、重启或前后台切换时的行为是否明确？
- 新增或变化的 UI 是否定义加载、无数据、错误、重试和版本不一致状态？

### 7.2 端间影响识别

- 需求是否涉及固件与 App、云端、算法或第三方 SDK 之间的数据、命令或状态协作？
- 如果涉及，是否能识别固件是提供方、消费方、双向参与，或当前仍待确认？
- 涉及项是否形成后续各端共同确认协议、数据或状态契约的提醒？
- 不在 PRD 阶段要求产品直接定义字段、单位、协议格式、时序、重试或幂等方案。

### 7.3 版本与 OTA

- 需求涉及版本差异时，最低或推荐 App 与固件版本、适用范围和灰度范围是否明确？
- 涉及跨端版本时，新旧组合的功能、文案、数据展示和降级是否一致？
- 涉及升级时，中断、失败、回滚或资源不一致是否可启动、可恢复且不损坏数据？

### 7.4 页面、翻译与语音资源输入

- 是否明确页面数量，以及是否存在多个页面之间的联动？
- 页面复杂度是否发生变化，例如新增复杂列表、表单、状态展示或分支交互？
- 是否涉及翻译或多语言，翻译范围和词条来源是否需要后续确认？
- 是否涉及语音资源，语音内容、语言范围和资源提供方式是否需要后续确认？
- 页面或交互发生变化时，是否提供可访问的设计稿或交互稿链接？
- 图片、字体和动效不作为本维度的默认检查项。
