# Firmware Doc Reviewer

固件侧研发流程文档的统一评审 Skill。它根据用户指令、文档标题和正文关键词识别文档类型，再加载 `rules/` 中对应的评审规则，输出有证据、可追踪、可执行的固件评审结论。

当前版本支持 **PRD Review**，用于判断产品需求文档是否具备进入固件研发阶段的条件，并给出评分、Block、风险、待确认项、关闭条件和验收建议。

## 适用场景

当请求中出现 PRD、产品需求文档、需求评审、固件侧 PRD review、手表端 PRD review、嵌入式 PRD review 等表达时使用本 Skill。

典型目标包括：

- 识别 PRD 中真正影响固件交付的需求与依赖
- 判断需求边界、状态机、可靠性、验证闭环等信息是否充分
- 区分固件主责、固件依赖其他端、其他端依赖固件和纯其他端事项
- 输出可审计的通过/有条件通过/不通过结论
- 给出明确的 Block 证据、影响、责任人与关闭条件

## 当前支持范围

| 文档类型 | 识别方式 | 规则文件 |
|---|---|---|
| PRD / 产品需求文档 | 用户明确指定，或标题/正文命中 PRD、产品需求文档、需求评审等表达 | `rules/prd-review.md` |

无法匹配已有规则时，Skill 会说明暂不支持，并列出识别到的关键词，不会强行套用 PRD 规则。同时命中多种文档类型且会改变评审方法时，会先确认主文档类型。

## 输入

最小输入包括：

1. PRD 链接或正文；
2. 文档中给出的目标产品/平台和涉及范围；
3. 手表固件、App、云端、算法、第三方 SDK 等涉及端中的至少一项。

建议同时提供 PRD 明确关联的交互稿、状态矩阵、协议、翻译或语音资源、埋点、硬件能力资料、OTA/回滚策略、历史数据样本和验收入口。Skill 会先阅读理解与当前需求必要相关的关联资料；无法访问的资料会被记录为证据缺口，只有该缺口实质影响需求边界、实现、兼容、安全或验收时才构成 Block。

## 评审原则

- **默认只读**：不修改文档，不创建 Jira，不提交代码，不发布固件。
- **证据优先**：以当前文档和明确关联资料为证据，不把推断写成事实。
- **设备范围忠于原文**：直接提取目标产品、首发设备、适配与验收范围，不根据型号名称或产品知识猜测设备身份。
- **不过度要求版本号**：具体固件/App 版本号不是默认必填；只有需求明确涉及版本差异、升级、降级、兼容、灰度或协同发布时才启用版本维度。
- **代码仓库不是默认输入**：仅在用户明确要求核对代码、复用能力存在争议或结论必须确认已有能力时，增加独立的实现可行性确认。
- **只评估固件相关内容**：纯其他端事项不进入固件评分和报告正文；必要跨端依赖仅按其对固件实现、兼容、可靠性、验收或发布的影响评估。
- **按适用维度折算**：不适用维度直接跳过，不输出“不适用”，最终按适用维度权重折算为 100 分。

## PRD 评审流程

1. 阅读当前 PRD 及必要关联文件。
2. 将需求拆成可独立归属和验收的最小需求项。
3. 判断每项直接责任端以及与固件的主责/依赖关系。
4. 提取固件实际变化：页面、既有展示、设备交互、状态分支、本地文案、跨端输入输出和业务逻辑。
5. 建立“用户动作 → App/云/算法输入 → 固件状态与数据 → UI/日志输出 → 失败与恢复”的端到端链路。
6. 仅在明确涉及版本或升级时建立版本组合矩阵。
7. 筛选适用评分维度，记录证据、扣分理由和改进建议。
8. 单独列出 Block、待确认项、风险和关闭条件。
9. 使用固定模板生成结构化报告，并明确标注推断。

## 评分维度

规则提供以下候选维度，只有适用项参与评分：

- 设备能力与需求边界（15）
- 端间协议与数据契约（15）
- 版本、兼容与升级策略（15）
- 功能流程与状态机（15）
- 页面、翻译与语音资源输入（15）
- 安全、可靠性与异常恢复（10）
- 可验证性与发布闭环（10）
- 实现范围与依赖治理（5）

结论规则：

- **通过**：总分不低于 80、Block 为 0，且无未确认的安全或兼容风险。
- **有条件通过**：总分 70–79 且 Block 为 0；可启动技术方案，但必须完成报告中的必补项。
- **不通过**：任一适用维度落入 Block 区间，或总分低于 70。

分数表示信息完整度和风险可控度，不代表项目优先级或研发工期。

## 强制 Block 边界

需求明确涉及特定设备、版本差异、升级、降级、兼容、灰度或协同发布，但对应策略、范围或恢复条件缺失；升级可能不可恢复或损坏数据；或固件及必要跨端依赖无法在目标环境验收时，可形成强制 Block。

仅缺少具体版本号、OTA 日志、发布记录、构建证据、机型清单，或仅出现不同设备名称，本身不能单独构成 Block。协议、页面、翻译、语音和设计稿输入缺口默认先作为提醒或待确认项，除非已经实质阻断固件交付。

## 输出结构

评审报告严格使用 `rules/prd-review.md` 规定的模板与顺序：

1. **关键信息**：评审对象、PRD 版本、结论、总分、Block 数、是否可进入下一阶段。
2. **主要依据**：支撑结论的核心证据。
3. **Block**：类型、证据、影响、关闭条件和责任人。
4. **最高优先级风险与建议**。
5. **详细信息**：基本信息、待确认项、固件实际变化、需求项与端侧归属、评分明细、必要跨端依赖、资源输入、影响端清单、必要时的版本/设备/网络矩阵，以及可执行验收清单。

不适用或与固件无关的章节直接省略；不得自由改变模板结构，也不输出额外的“已阅读资料”章节。

## 使用方式

将仓库作为 Agent Skill 安装后，在请求中提供 PRD 链接或正文并明确提出固件评审，例如：

```text
请使用 firmware-doc-reviewer 评审这份 PRD，重点判断是否具备进入固件研发阶段的条件，并按固定模板输出。
```

如果关联资料无法由 Agent 访问，请在请求中附上正文或导出文件，以便形成完整证据链。

## 目录结构

```text
firmware-doc-reviewer/
├── SKILL.md              # 文档类型路由、通用边界和扩展约定
├── agents/openai.yaml    # Agent 展示信息与默认提示词
└── rules/
    └── prd-review.md     # PRD 输入、流程、评分、Block 与输出模板
```

## 扩展新的文档类型

本项目坚持单 Skill、多规则文件的扩展方式：

1. 在 `rules/` 下新增对应 Markdown 规则；
2. 在 `SKILL.md` 的路由中补充识别关键词与目标规则文件；
3. 不为每种文档类型创建独立 Skill；
4. 执行时只加载当前文档类型需要的规则。
